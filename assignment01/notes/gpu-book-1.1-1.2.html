GPU 用更低的单线程性能，换取更高的总吞吐

本书讲解 CUDA Programming Guide（下文称 Guide）的第 1.1 节和第 1.2 节，读者只需会写 C 语言的 for 循环。

第一部分比较同一台服务器里的 CPU 和 GPU 的规格，再用一个 CPU 实验测出延迟、吞吐和并行度之间的关系。第二部分讲 CUDA 如何组织线程、硬件如何执行线程、数据存放在哪里。

为什么用 GPU（Guide 1.1）

§1同一台服务器里，CPU 和 GPU 的规格差在哪里

问题

Guide 1.1.2 说，在相近的价格和功耗下，GPU 的指令吞吐和内存带宽都远高于 CPU。具体高多少？代价是什么？

数据

NVIDIA DGX A100 服务器同时装有 AMD EPYC 7742 CPU 和 NVIDIA A100 GPU。下表比较一颗 EPYC 7742 和一块 A100（40 GB 版）的公开规格。

  • TFLOPS：每秒 1012 次浮点运算。
  • FP32：32 位单精度浮点数。
  • FMA（fused multiply-add）：一条指令完成 a×b+c，计为 2 次浮点运算。
  • SM（Streaming Multiprocessor）：GPU 的基本计算单元，§6 详述。
  • 驻留线程：已分配到核心上、硬件随时可以切换过去执行的线程，它不一定在当前时钟周期执行。EPYC 7742 每核支持 2 个硬件线程（SMT）；A100 每个 SM 最多驻留 2048 个线程。
规格EPYC 7742（1 颗）A100 40 GB（1 块）A100 / 7742
核心64 核108 个 SM
时钟频率基频 2.25 GHz，加速 3.4 GHz加速 1.41 GHz0.63×（1.41 / 2.25）
可同时驻留的硬件线程128（64 核 × 2）221,184（108 × 2048）1,728×
FP32 峰值4.6 TFLOPS19.5 TFLOPS4.2×
内存带宽204.8 GB/s（8 通道 DDR4-3200）1,555 GB/s（HBM2）7.6×

FP32 峰值的算法：EPYC 7742 为 64 核 × 2.25 GHz × 32 FLOP/周期（每核 2 条 256 位 FMA 流水线 × 8 个 FP32 × 2）= 4.6 TFLOPS。A100 为 108 SM × 64 个 FP32 单元 × 2 × 1.41 GHz = 19.5 TFLOPS。两者都按厂商标称峰值所用的频率计算：EPYC 7742 用基频 2.25 GHz，A100 用加速频率 1.41 GHz。时钟频率之比也按这两个频率计算。

原因

Guide 1.1.2 给出的原因是晶体管的分配：GPU 把更多晶体管用于数据处理，CPU 把更多晶体管用于缓存和控制流（分支预测、乱序执行等）。

“…trading off lower single-thread performance to achieve much greater total throughput.”Guide 1.1.2

结论

一块 A100 与一颗 EPYC 7742 相比，FP32 峰值高 4.2 倍，内存带宽高 7.6 倍，可同时驻留的硬件线程多 1,728 倍，时钟频率只有后者的 0.63 倍。

把 FP32 峰值平均到每个驻留线程：A100 为 19.5 TFLOPS ÷ 221,184 ≈ 0.088 GFLOPS，EPYC 7742 为 4.6 TFLOPS ÷ 128 ≈ 36 GFLOPS，相差约 400 倍。也就是说，A100 必须让大量线程同时工作，才能达到峰值。§2 用实验说明原因。

§2达到峰值吞吐需要多少个独立操作

两个术语：

  • 延迟（latency）：一个操作从发出到结果可用所需的时间，单位是秒。
  • 吞吐（throughput）：单位时间内完成的操作数，例如 TFLOPS（浮点运算/秒）和 GB/s（字节/秒）。

§1 表中的 FP32 峰值和内存带宽都是吞吐，都不包含延迟的信息。

问题

CPU 的加法器是流水线结构：它每隔 Δ 秒可以接收一个新的加法，每个加法要经过 L 秒才出结果（L > Δ）。如果每个加法都要用上一个加法的结果，会发生什么？

假设

如果每个加法都依赖上一个加法的结果，加法器每 L 秒只能完成一个加法，吞吐为 1/L。要达到峰值吞吐 1/Δ，同时在流水线中的独立加法至少要有 L/Δ 个。

这就是 Little 定律：在途操作数 = 吞吐 × 延迟。

验证

程序固定做 N = 4.8 亿次 double 加法，分给 K 条互不依赖的累加链。K = 1 时每次加法都依赖上一次；K = 4 时同一时刻有 4 个互不依赖的加法。以下是 K = 1 和 K = 4 的循环：

// K = 1：s0 的每次加法都要等上一次的结果
for (long i = 0; i < N; i++) { s0 += x; }

// K = 4：四条链互不依赖，可以同时在流水线里
for (long i = 0; i < N/4; i++) { s0 += x; s1 += x; s2 += x; s3 += x; }

完整源码在仓库的 assignment01/notes/ilp_chains.c，复现命令为：

gcc -O2 -fno-tree-vectorize -o ilp_chains ilp_chains.c && ./ilp_chains
  • -fno-tree-vectorize 禁止编译器把多条链合并成 SIMD 指令，保证每次加法都是一条标量 addsd 指令。
  • 没有加 -ffast-math。加了它，编译器可以把 s0 拆成几个部分和分别累加，相当于把 K = 1 改成了 K > 1；不加，K = 1 的加法就必须按源码顺序逐个执行。
  • 反汇编确认了这一点。编译器把 K = 1 的循环展开了 2 次，每轮执行两条 addsd %xmm2,%xmm1，各对应源码的一次 s0 += x。%xmm1 保存 s0，%xmm2 保存 x；两条指令都读写 %xmm1，所以第二条必须等第一条的结果。
K（独立链数）12481216
每次加法耗时（ns，4 次中位数）0.5280.2660.1450.1320.1330.133
占峰值吞吐的比例25%50%91%100%99%99%
原因

K = 1 时，每条 addsd 都要等上一条的结果，所以 0.528 ns 就是这台机器上一次 double 加法的延迟 L。

K ≥ 8 时，耗时稳定在 0.132 ns，这是加法器的吞吐上限，对应 Δ。

L/Δ = 0.528 / 0.132 = 4.0，假设预测需要约 4 条独立链。实测 K = 4 时达到峰值的 91%，K = 8 时达到 100%。

结论

在这台 Xeon 上，只有一条依赖链时，double 加法的吞吐只有峰值的 25%；要达到峰值的 91% 以上，至少需要 4 条独立链（实测 K = 4）。

所需的独立操作数等于延迟 ÷ 每个操作的发射间隔（这里是 4.0）。

GPU 也遵循同一规律

§2 实验中，独立的加法由程序员写在同一个线程里。GPU 的独立操作主要来自不同的线程：一个 warp（32 个线程一组，§8 详述）等待结果时，SM 切换去执行另一个 warp。

“Executing other warps when one warp is paused or stalled is the only way to hide latencies and keep the hardware busy.”CUDA C++ Best Practices Guide，Occupancy 一节

按 §2 的规律，GPU 需要的驻留线程数取决于它的延迟和发射间隔。本书没有测量 GPU 的这两个值。作业 prob 1.5 会在 GPU 上测量不同线程数下的耗时。

§3依赖链长度决定执行时间的下限

问题

换一块峰值吞吐更高的处理器，是否总能让程序更快？

推理

把计算画成依赖图：节点是操作，边从被依赖的操作指向依赖它的操作。图中最长路径上的操作只能逐个执行，每个至少耗时 L。所以执行时间 ≥ 最长路径的节点数 × L，这个下限与处理器的吞吐无关。

§2 实验中 K = 1 的情形就是这种情况：这颗 CPU 核的加法吞吐是 1/0.132 ns，但单条依赖链只用上了其中的 25%。

结论

一个计算在任何处理器上的执行时间，都不低于“依赖图最长路径的操作数 × 单个操作的延迟”。

GPU 只有在每一步都有大量互相独立的操作时，才能比 CPU 快。如果最长路径几乎等于操作总数，GPU 的高吞吐用不上，而 GPU 每个线程分到的峰值算力只有 CPU 的约 1/400（§1）。

编程模型（Guide 1.2）

第一部分说明了 GPU 需要大量互相独立的线程才能达到峰值吞吐。第二部分讲 CUDA 如何创建和组织这些线程、硬件如何执行它们、它们读写的数据放在哪里。

§5host 与 device（Guide 1.2.1）

CUDA 假定系统中同时有 CPU 和 GPU：

  • host：CPU 及其直连的内存（host memory）。
  • device：GPU 及其直连的显存（device memory）。

程序从 CPU 上开始执行。在 GPU 上运行的代码叫 device code。从 host 启动、在 device 上执行的函数叫 kernel，在 CUDA C++ 中用 __global__ 标记。启动 kernel 叫 launch，一次 launch 会创建大量线程，每个线程都执行同一个 kernel 函数。

从 for 循环到 kernel

CPU 上的向量加法由一个线程执行 n 次循环体：

for (int i = 0; i < n; i++)
    c[i] = a[i] + b[i];

CUDA 的写法是把循环体写成 kernel，launch 至少 n 个线程，每个线程执行一次循环体。每个线程用内置变量（§7）算出自己负责的下标 i。i 的计算公式和越界检查是作业 prob 2.1 的内容。

n 次循环之间没有依赖，所以依赖图的最长路径只有 1 个操作（§3），每个线程都可以并行执行。

§6GPU 由许多 SM 组成（Guide 1.2.2）

对编程来说，一块 GPU 是一组 SM（Streaming Multiprocessor）。若干 SM 组成一个 GPC（Graphics Processing Cluster）。每个 SM 包含：

  • 计算单元：例如 A100 每个 SM 有 64 个 FP32 单元。
  • 寄存器堆：A100 每个 SM 有 65,536 个 32 位寄存器，共 256 KB。
  • 统一数据缓存：同时用作 shared memory 和 L1 缓存，两者的比例可在运行时配置。A100 每个 SM 合计 192 KB。

§7thread、block、grid（Guide 1.2.2.1）

一次 launch 创建的线程分为两层：

  • 若干 thread 组成一个 thread block（简称 block，也叫 CTA，cooperative thread array）。一个 block 最多有 1024 个线程。
  • 若干 block 组成一个 grid。同一个 grid 中所有 block 的形状相同。
  • block 和 grid 都可以是一维、二维或三维。

launch 时，程序通过 execution configuration（执行配置）指定 grid 和 block 的维度。CUDA C++ 中的写法见 Guide 2.1。

kernel 中的每个线程通过四个内置变量确定自己的位置：

  • threadIdx：线程在 block 中的下标。
  • blockIdx：block 在 grid 中的下标。
  • blockDim：block 的维度。
  • gridDim：grid 的维度。

Guide 规定的两条调度规则

  1. 一个 block 的所有线程在同一个 SM 上执行，因此它们可以通过该 SM 上的 shared memory 交换数据，也可以在 block 内同步。
  2. block 之间没有调度顺序的保证。block 可以任意顺序、并行或串行地执行，所以一个 block 不能依赖另一个 block 的结果。

第 2 条使同一个程序可以不经修改地运行在 SM 数量不同的 GPU 上：一个 grid 可以有数百万个 block，而一块 GPU 只有几十到一百多个 SM，硬件把 block 依次分配给有空闲资源的 SM。

复现方法：在有 GPU 的机器上多次运行作业 prob 0.1 的程序（4 个 block，每个 block 8 个线程），比较各次输出中 block 的顺序。命令为 cd assignment01/cuda && make run/m0_env/01_hello。按第 2 条规则，各次运行的顺序可以不同。

thread block cluster（Guide 1.2.2.1.1）

compute capability 是 NVIDIA 给每代 GPU 架构编的版本号，例如 A100 是 8.0，H100 是 9.0。在 compute capability 9.0 及以上的 GPU 上，可以在 block 之上再分一层 cluster，A100 不支持这一层。一个 cluster 内的 block 同时在同一个 GPC 上执行，它们可以互相同步，也可以访问彼此的 shared memory（称为 distributed shared memory）。划分 cluster 不改变 grid 的维度和 block 的下标。

§8warp 与 SIMT（Guide 1.2.2.2）

SM 执行 block 时，把 block 中的线程按顺序每 32 个分为一组，称为 warp。warp 内的线程称为 lane，编号为 0–31。

如果 block 的线程数不是 32 的倍数，最后一个 warp 中的部分 lane 不执行任何工作。以 100 个线程的 block 为例：

  • 它被分成 ⌈100/32⌉ = 4 个 warp，共 128 个 lane。
  • 其中 28 个 lane 空闲，占 22%。

因此 Guide 建议 block 的线程数取 32 的倍数。

SIMT 与 warp divergence

warp 按 SIMT（Single Instruction, Multiple Threads）方式执行：同一 warp 的线程执行同一个程序，但每个线程可以走不同的分支。

当同一 warp 中的线程走了不同分支时，硬件依次执行每条分支路径，不在当前路径上的线程被屏蔽（masked off），这称为 warp divergence。它会降低计算单元的利用率。例如：

if (threadIdx.x % 2 == 0) { A(); }   // 偶数 lane
else                      { B(); }   // 奇数 lane

SIMT 与 SIMD 的区别

CPU 的 SIMD 指令（例如 AVX）用一条指令处理一个固定宽度的向量寄存器。Guide 1.2.2.2 列出的区别如下：

SIMD（如 AVX）SIMT（GPU warp）
程序员编写的代码对整个向量的操作单个线程的标量代码
控制流整个向量共用一个控制流每个线程可以有自己的控制流
数据宽度由指令固定（如 256 位）不出现在指令中

Guide 同时要求：程序不得假定同一 warp 的线程总是逐条指令同步推进（lockstep）。例如，一个线程不经同步就读取同一 warp 另一线程刚写入 shared memory 的值，就依赖了这一假定。违反这条要求的程序行为未定义，在不同架构上可能不同。图 8 只是一种可能的执行顺序，Guide 并不保证 warp 一定按这个顺序执行。

§9tile 编程模型（Guide 1.2.2.3）

SIMT 模型中，程序员编写单个线程的代码。Guide 介绍的第二种模型是 tile 编程：程序员编写整个 block 的代码，操作对象是多维数据块（tile）。下面用 Python 写出同一个逐元素运算 y = 2x + 1 在两种模型下的形式：

# SIMT：kernel 描述一个线程处理一个元素，i 由线程下标算出
def simt_kernel(i):
    y[i] = x[i] * 2 + 1

# tile：kernel 描述一个 block 处理一个长度为 TILE 的数据块
def tile_kernel(block_id, TILE=64):
    s = block_id * TILE
    t = x[s:s+TILE]              # 读入一个 tile
    y[s:s+TILE] = t * 2 + 1      # 对整个 tile 运算；线程如何分工由编译器决定

tile 模型的规则（Guide 1.2.2.3）：

  • 程序员只指定 grid 的维度，每个 block 的线程数由编译器决定。
  • 一个 block 只有一条控制流，所以不存在 warp divergence。
  • array 是 device memory 中可修改的多维数据；tile 是 block 内不可修改的值，存放位置（寄存器、shared memory 等）由编译器决定。
  • tile 的每一维长度必须是 2 的幂，并在编译时已知。
  • 两种模型可以在同一程序中共存，按 kernel 选择。需要控制单个线程的行为时仍使用 SIMT。

作业 Module 7 使用的 Triton 和 TileLang 采用 tile 模型。

§10存储层次（Guide 1.2.3）

下表列出 kernel 能访问的存储，容量以 A100 40 GB 为例。表中“访问范围”指能直接读写该存储的线程集合。

存储位置访问范围A100 容量
寄存器SM 内单个线程256 KB / SM
shared memorySM 内同一 block（或 cluster）的线程≤ 164 KB / SM
L1 缓存SM 内，与 shared memory 共用 192 KB由硬件管理192 KB 减去 shared

A100 的 192 KB 统一数据缓存中，最多 164 KB 可以配置为 shared memory，其余至少 28 KB 用作 L1。

访问延迟随离 SM 的距离增加。CUDA C++ Best Practices Guide 的 Shared Memory 一节给出：在没有 bank conflict 时，shared memory 的延迟约为未缓存的 global memory 的 1/100。

shared memory 分为 32 个 bank。同一 warp 的多个线程同时访问同一个 bank 的不同地址时，这些访问会被串行执行，这就是 bank conflict。

global memory 与 host memory（Guide 1.2.3.1）

GPU 的 DRAM 在 device code 中称为 global memory，同一块 GPU 的所有 SM 都能访问。CPU 和 GPU 共用一个统一虚拟地址空间：由一个地址可以判断它属于 CPU 内存还是哪一块 GPU 的显存。分配、复制和数据位置由 CUDA API 显式控制。

大型 GPU 内部可能分为多个 locality domain（Guide 1.2.3.2）。每个 domain 包含一部分显存和 SM，把数据和处理它的 SM 放在同一 domain 可以提高性能，但不影响正确性。

寄存器与 shared memory 的容量限制（Guide 1.2.3.3）

寄存器由编译器分配给线程的局部变量。shared memory 按 block 分配，不按线程分配。一个 block 只有在下面两个条件都满足时才能在 SM 上启动：

每线程寄存器数 × block 线程数 ≤ SM 的寄存器数
block 的 shared memory 用量  ≤ SM 可用的 shared memory

以 A100 为例，SM 有 65,536 个寄存器：

  • 一个 1024 线程的 block，每线程用 64 个寄存器时共需 65,536 个，正好装下。
  • 每线程用 65 个寄存器时超出 SM 容量，这个 block 无法启动，只能减少 block 的线程数。

缓存（Guide 1.2.3.3.1）

  • L1：每个 SM 一个，位于统一数据缓存中。
  • L2：整块 GPU 共享。
  • constant cache：每个 SM 一个，缓存在 kernel 执行期间不变的数据。编译器可能把 kernel 参数放在这里。

§11unified memory（Guide 1.2.3.4）

不使用 unified memory 时，CPU 代码只能访问 host memory，kernel 只能访问 device memory，数据需要显式复制（图 4 的第 ② 和第 ⑤ 步）。

Unified memory 是一种分配方式：分配出的内存可以同时被 CPU 和 GPU 访问，由 CUDA 运行时或硬件按需在两侧之间迁移数据。迁移本身有开销，所以性能仍取决于迁移次数，以及数据是否靠近访问它的处理器。作业 cuda/m2_first_kernel/02_vector_add_um.cu 是使用 unified memory 的版本。

Guide 还提到 mapped memory：GPU 经 PCIe 或 NVLink 直接访问 CPU 内存。它的延迟比显存高、带宽比显存低，不能代替显存使用。
