而不是更快的 CPU

AI 时代，kernel 越来越多是 AI 帮你写的。但判断它写得对不对、快不快，靠的是你脑子里那张 GPU 的“心智地图”。这本小书只做一件事：用 20 分钟把这张地图装进你脑子里。

§0读之前：先认识五个词

后面每一节都会反复用到这几个词。现在不必完全理解，有个印象就行。

延迟 latency
一件事从开始到完成要多久。单位是时间，比如“一次显存读要 ~500 ns”。
吞吐 throughput
单位时间能完成多少件事。单位是“件/秒”，比如 “19.5 TFLOPS” = 每秒 1.95×1013 次浮点运算。
带宽 bandwidth
存储系统的吞吐：每秒能搬多少字节，比如 “2 TB/s”。
并行 parallelism
同一时刻有多少件互不依赖的事在同时推进。
kernel
在 GPU 上运行的函数。一次启动会让成千上万个线程同时执行同一份代码。
贯穿全书的一句话

延迟和吞吐是两个不同维度的量。吞吐高不代表延迟低，反之亦然。GPU 的全部设计，都是“牺牲单件事的速度，换总的完成量”。

为什么 AI 时代还要学这个

你可以让 AI 写 kernel，但 AI 写出来的东西常见三种翻车：结果偶尔不对（依赖了 block 顺序）、跑得比 CPU 还慢（并行宽度不够、访存乱跳）、换张卡就崩（资源超限）。这三类问题，本书的五个心智模型各管一块。有了它们，你才能当好 AI 的 reviewer。

1.1

引言：GPU 是什么，为什么用它

INTRODUCTION

1.1.1GPU 从哪来

GPU（Graphics Processing Unit）最初是给 3D 图形用的固定功能硬件：把三角形变换到屏幕、给每个像素上色。图形有个天然特点：屏幕上几百万个像素，每个像素的计算几乎一样、又彼此独立。于是硬件设计者造了大量简单的计算单元，让它们同时处理不同的像素。

后来这些单元变得可编程（可以写 shader）。人们发现，只要问题也长成“大量相同、独立的小计算”的样子，比如矩阵乘、物理模拟、神经网络，就能借用这股算力。2006 年 NVIDIA 推出 CUDA，让你不用假装在画图，直接用类 C++ 的语言给 GPU 写通用程序。

1.1.2用 GPU 的好处：晶体管花在哪里

想象两家餐厅，装修预算一样。CPU 餐厅请了 8 位米其林大厨，配超大冷库和一个聪明的经理，每道菜都做得飞快，还会提前猜你下一道点什么。GPU 餐厅雇了一万个只会照单炒菜的厨工，每 32 人共用一个喊口令的领班，冷库很小，但进货通道特别宽。点一份菜，CPU 餐厅先上；来一万人的团餐，GPU 餐厅完胜。

Guide 的核心论断只有一句：在相近的价格和功耗下，GPU 的指令吞吐和显存带宽都远高于 CPU。代价写得也很直白：

“trading off lower single-thread performance to achieve much greater total throughput.”
用更低的单线程性能，换取大得多的总吞吐。（Guide 1.1.2）

为什么会这样？芯片面积和功耗是有限预算。CPU 和 GPU 把同一笔晶体管预算花在了不同地方：

CPU 把预算花在“让一个线程尽快跑完”

  • 大缓存：把常用数据放在离核很近的地方，减少等内存的时间。
  • 乱序执行、分支预测：猜下一步要做什么，提前去做，把等待藏起来。
  • 高主频：4–5 GHz，单条指令很快。

结果：一个 CPU 核处理一串前后依赖的计算非常快，但一颗芯片上只有几个到几十个这样的核。

GPU 把预算花在“让很多线程一起推进”

  • 大量 ALU：一块数据中心 GPU 有上万个计算 lane。
  • 控制逻辑很省：一组 32 个线程共用一套取指/译码（这就是后面的 warp）。
  • 主频较低：1–2 GHz。单个线程跑得比 CPU 慢。
  • 宽显存总线：HBM 把显存颗粒和 GPU 封装在一起，用极宽的总线换带宽。
维度CPU（典型服务器）GPU（以 A100 为例）
同时运行的线程几十108 SM × 2048 ≈ 22 万
主频3–5 GHz~1.4 GHz
FP32 峰值数 TFLOPS19.5 TFLOPS
访存带宽~100–400 GB/s1.5–2.0 TB/s
擅长串行、分支多、依赖链长大量独立、相同的计算

A100 数字来自 NVIDIA 公开规格；你用的卡请以 prob 0.2 的 device query 结果为准，并按 handout 的要求把型号和 compute capability 一起记下。

CPU 把晶体管花在“让一个人跑得快”，GPU 花在“让很多人一起跑”。这是设计取舍，不是谁的工艺更先进。

深入延迟与吞吐：本章最重要的一对概念

Guide 1.1 其实没有出现 “latency” 这个词，它说的是“单线程性能 vs 总吞吐”。但讲座和作业都用“延迟/吞吐”来表述，二者是一回事。这里把它彻底讲清楚。

类比：跑车和大巴。要把 400 人从北大送到清华。跑车 5 分钟一趟、一次 2 人；大巴 15 分钟一趟、一次 50 人。跑车每一趟的延迟低，大巴每趟延迟高，但大巴的吞吐（人/分钟）高得多。CPU 是跑车，GPU 是一个大巴车队。

“TFLOPS”是一个吞吐数字

标称的 TFLOPS 是 （计算单元个数）×（每单元每周期运算数）×（主频） 乘出来的总量。它描述“所有单元都在忙时，每秒一共做多少次运算”。它不告诉你某一次运算从发出到出结果要多久。一条 GPU 指令的延迟是若干个时钟周期，而 GPU 的时钟比 CPU 慢。

// A100 FP32 峰值的来历（粗算）
108 SM × 64 FP32 单元/SM × 2 FLOP/周期(FMA) × 1.41 GHz
  ≈ 19.5 TFLOPS      // 前提：几千个单元每个周期都有活干

“高带宽”也是吞吐

HBM 的 TB/s 级带宽，是在大块、连续、对齐的访问下测出的。每次读显存的延迟依然是几百纳秒量级。带宽能跑满，靠的是同时在路上的请求足够多，并且每次请求搬的都是有用的连续字节。Module 4 会用 05_bandwidth.cu 让你亲手测这个。

吞吐需要“足够多互不依赖的工作”

GPU 掩盖延迟的手段是：一个 warp 在等内存时，硬件立刻切到另一个准备好的 warp 去算。这要求手头始终有很多个可以同时做的任务。

用一个十行的 Python 玩具模型感受一下。它不是 GPU 的真实行为，只是把“延迟高但并行宽”这件事算给你看：

# 玩具模型：n 个互不依赖的任务
def finish_time(n, latency, width):
    """每个任务耗时 latency，机器一次能同时做 width 个"""
    rounds = -(-n // width)          # 要分几轮做完
    return rounds * latency

n = 1_000_000
print("CPU", finish_time(n, latency=1,  width=16))     # 62500
print("GPU", finish_time(n, latency=20, width=50_000)) # 400
print("GPU, n=1", finish_time(1, latency=20, width=50_000)) # 20，比 CPU 的 1 慢

同一台“GPU”，任务多时快 150 倍，只有一个任务时反而慢 20 倍。作业 prob 1.5 里 <<<1,1>>> 那一行，你会在真机上看到同样的现象。

判断一个任务适不适合 GPU

先问：同一时刻有多少件互不依赖的事？如果答案是几万、几百万，GPU 能发挥。如果每一步都卡在上一步，上面玩具模型里的 width 实际上就退化成了 1。剩下的你可以在 prob 1.2 里自己推。

这个思路和 Amdahl 定律同源：程序里串行的部分，决定了加速比的上限。

先看宽度，再看总量。TFLOPS 和 TB/s 都是“所有人都在忙”时的上限，前提是有足够多的独立活给他们干。

1.1.3快速上手：不一定要手写 kernel

层次例子你写什么
AI 框架PyTorch、JAXy = x @ w，框架去调 GPU

1.2

编程模型：线程怎么组织，数据放在哪

PROGRAMMING MODEL

1.2.1异构系统：CPU 是指挥，GPU 是工厂

CPU 是项目经理，GPU 是外包工厂。经理在办公室（host）写好图纸、把原材料用卡车（PCIe）运到工厂仓库（显存），一声令下开工，然后可以先去忙别的，最后再把成品运回来。卡车很慢，所以聪明的经理尽量少跑几趟。

CUDA 假设机器里同时有 CPU 和 GPU。两边各有自己的内存：

  • host（主机）= CPU + 它直连的内存（host memory）
  • device（设备）= GPU + 它直连的显存（device memory）

程序总是从 CPU 上的 main 开始。CPU 负责准备数据、把数据拷到 GPU、启动（launch）kernel、等结果、把结果拷回来。

device code
在 GPU 上运行的代码。
kernel
从 host 启动、在 device 上运行的函数。CUDA C++ 里用 __global__ 标记。
launch
启动 kernel。一次 launch 会创建很多线程，它们都执行这同一个函数。

思维上最关键的一步转换：CPU 程序写的是“一个循环做 n 次”，GPU kernel 写的是“我是第几号工人，我只做我那一份”。

# CPU 思维：一个人做完所有
for i in range(n):
    c[i] = a[i] + b[i]

# GPU 思维：把循环体拿出来，变成“每个工人的工作说明书”
def kernel(my_id):               # my_id 由硬件告诉你，不用自己循环
    c[my_id] = a[my_id] + b[my_id]
# 然后一次性叫来 n 个工人，同时执行 kernel

真实的 CUDA C++ 里，my_id 要由几个内置变量拼出来，还要处理“工人比活多”的情况。这正是 prob 2.1 的几个空，留给你自己填。

1.2.2GPU 硬件模型：一堆 SM

对写程序来说，一块 GPU 可以看成一堆 SM（Streaming Multiprocessor，流式多处理器），SM 再分组成 GPC（Graphics Processing Cluster）。SM 是你最需要记住的硬件单位：

1.2.2.1Thread、Block、Grid：三层线程组织

一次 launch 创建的线程不是一盘散沙，而是分成两层：

  • 若干 thread 组成一个 thread block（也叫 CTA）。
  • 若干 block 组成一个 grid。同一个 grid 里所有 block 形状相同。
  • block 和 grid 都可以是 1D、2D 或 3D，方便对应向量、图像、体数据。
学校类比。thread 是学生，block 是一个班，grid 是整个年级，SM 是教室。全年级几千个班，教室只有一百多间：哪个班先进教室上课、哪个班后上，教务处随便排，你没法指定。

launch 时你通过 execution configuration（执行配置）告诉 GPU：grid 多大、每个 block 多大。CUDA C++ 里的具体写法见 Guide 2.1，作业 prob 2.1 会让你亲手写。

每个线程靠内置变量知道“我是谁”：blockIdx（我在第几个班）、threadIdx（我在班里第几号）、blockDim / gridDim（班有多大、年级有多少班）。由这些量可以拼出全局唯一的学号，每个线程据此去处理不同的数据。

下面这段 Python 就是 launch 的“心智模拟器”。注意 shuffle 那一行，它就是规则 2：

import random

def launch(kernel, grid, block):
    blocks = list(range(grid))
    random.shuffle(blocks)            # block 顺序：没有任何保证！
    for b in blocks:                  # 真机上很多 block 同时在不同 SM 上跑
        for t in range(block):         # 同一个 block 的线程在同一个 SM 上
            kernel(blockIdx=b, threadIdx=t)

def hello(blockIdx, threadIdx):
    if threadIdx == 0:
        print(f"hello from block {blockIdx}")

launch(hello, grid=4, block=8)      # 每次运行输出顺序都可能不同

跑几次，再对照 prob 0.1 在真 GPU 上的输出。两者都乱序，原因是同一条规则。

两条必须记住的规则

规则 1 · block 是“整体搬家”的

一个 block 里的所有线程一定在同一个 SM 上运行。所以它们能通过 SM 上的 shared memory 交换数据、互相同步。

规则 2 · block 之间没有顺序保证

block 之间没有任何调度保证。block 7 可能比 block 0 先跑，也可能同时跑。所以你的程序必须在“block 以任意顺序、并行或串行执行”时都正确。不要让一个 block 等另一个 block 的结果。

这条规则也是 CUDA 程序能在 SM 数量不同的卡上不改代码就运行的原因。作业 0.1 让你多跑几次 hello，输出顺序变化就是它的直接体现。

班内可以说悄悄话（shared memory）、可以喊“都等一下”（同步）；班与班之间别互相等，因为你不知道对方什么时候上课。

1.2.2.1.1 Thread Block Cluster（选读）

从 compute capability 9.0（Hopper）开始，block 之上可以再加一层可选的 cluster。一个 cluster 里的 block 会被同时放到同一个 GPC 上，可以互相同步，还能读写彼此的 shared memory（称为 distributed shared memory）。cluster 不改变 grid 的大小和 block 编号。初学阶段知道有这一层即可。

1.2.2.2Warp 与 SIMT：硬件真正执行的单位

阅兵方阵。一个方阵 32 人，教官只喊一个口令，32 人同时出左脚。要是口令是“学号单数的向左转”，那双数同学只能原地站着等，等单数做完，再喊“双数的向右转”。同一时间只有一半人在动，这就是 divergence 的代价。

你按 block 组织线程，但 SM 执行时会把 block 里的线程每 32 个切成一组，叫做 warp。warp 内的 32 个线程叫 lane，编号 0–31。一个 warp 共享一套取指和译码：同一时刻，它们执行同一条指令，只是作用在各自的数据上。

SIMT 是什么

SIMT = Single Instruction, Multiple Threads。从程序员视角看，你写的是一个线程的代码，每个线程有自己的变量、可以走自己的分支。从硬件视角看，32 个线程一起执行。两者之间的差距，在遇到分支时显现：

if (threadIdx.x % 2 == 0)  { A(); }   // 偶数 lane 走这边
else                        { B(); }   // 奇数 lane 走那边

SIMT 和 SIMD 不一样在哪

CPU 上的 SIMD（如 AVX）是一条指令处理一个固定宽度的向量寄存器，比如 8 个 float。Guide 指出两者的区别：

SIMD（CPU 向量指令）SIMT（GPU warp）
你写的是对向量的操作单个线程的标量代码
控制流整条向量只有一个控制流，分支要自己用 mask 处理每个线程可以有自己的控制流，硬件负责 mask
数据宽度指令里写死（如 256-bit）不在指令里体现
Guide 的警告

不要依赖“warp 内线程一定步调一致（lockstep）”这种硬件细节。违反 SIMT 模型的写法属于未定义行为，在不同架构上表现可能不同。Volta 之后每个线程有独立的 program counter，这个变化具体意味着什么，是作业 prob 1.4 让你思考的。

你写的是一个线程的代码，硬件按 32 人一组执行。让同一个 warp 里的线程尽量走同一条路；block 大小取 32 的倍数。

1.2.2.3Tile 编程：另一种视角

SIMT 让你从“一个线程”的角度写代码。新版 Guide 介绍了第二种模型：tile 编程。你从“一整个 block”的角度写代码，操作的对象是一块多维数据（tile），比如 64×64 的矩阵块。

  • 你只指定 grid 大小；每个 block 用多少线程由编译器根据 tile 操作决定。
  • tile 块只有一条控制流，所以没有 warp divergence 这回事。
  • array 是放在显存里、可修改的多维数据；tile 是 block 内部的不可变值，编译器决定它放在寄存器、shared memory 还是别处。tile 的每一维都必须是 2 的幂、编译期已知。
  • 内置操作包括逐元素运算、矩阵乘、按轴归约（sum/max）、reshape/transpose、类型转换；形状不同的 tile 运算时会广播。
  • tile 不取代 SIMT。两者可以在同一程序里共存，按 kernel 选择；需要精细控制每个线程时仍然用 SIMT。

作业 Module 6、7 里的 Triton 和 TileLang 就是这种思路。用 NumPy 打个比方，差别一眼就能看出来：

# SIMT 视角：我是一个线程，只管一个元素（循环由硬件“展开”成很多线程）
def simt_kernel(i):
    y[i] = x[i] * 2 + 1

# Tile 视角：我是一个 block，一口吃下一整块
def tile_kernel(block_id, TILE=64):
    s = block_id * TILE
    t = x[s:s+TILE]                  # load 一个 tile
    y[s:s+TILE] = t * 2 + 1          # 整块运算，线程怎么分工交给编译器
SIMT：我是一个人。Tile：我是一个班，拿一整块数据一起处理。AI 写 Triton/TileLang 时，你脑子里要切换到第二种视角。

1.2.3GPU 存储：数据住在哪里

写作业时，资料放在哪？口袋里的小抄（寄存器）伸手就拿，但只有你自己能看；课桌上摊开的书（shared memory）同桌都能看；楼下图书馆（L2、显存）什么都有，但要走一趟；城另一头的档案馆（host memory）得坐车去。厉害的人会提前把要用的书搬上课桌。

写 GPU 程序，算力往往不是瓶颈，把数据搬到计算单元旁边才是。所以要清楚有哪些存储、谁能访问、离计算单元多远。

1.2.3.1 DRAM：global memory 与 host memory

GPU 的显存（DRAM），从 device code 的角度叫 global memory：这块 GPU 上所有 SM 都能访问。CPU 的内存叫 system / host memory。CPU 和 GPU 共享一个统一虚拟地址空间：每个地址都能判断它属于 CPU 还是哪块 GPU。但“地址能认出来”不等于“随便都能访问”，需要用 CUDA API 分配和拷贝。

1.2.3.2 Locality Domain（选读）

大型 GPU 内部可能分成几个 locality domain，每个 domain 有自己的一部分显存和 SM。把数据和处理它的 SM 放在同一 domain 更快。这只影响性能，不影响正确性，初学可以跳过。

1.2.3.3 片上存储：寄存器与 shared memory

每个 SM 上有两种程序员能直接用的片上存储：

寄存器 RegisterShared Memory

一个 block 能被放到 SM 上运行，前提是它要的资源装得下：

每线程寄存器数 × 每 block 线程数 ≤ SM 的寄存器堆
每 block 的 shared memory     ≤ SM 可用的 shared memory

装不下就启动不了，只能缩小 block。装得下的话，一个 SM 能同时驻留几个 block 也由这些量决定。Module 4 的 occupancy 题会让你手算，那时会用到 prob 0.2 填的表。

1.2.3.3.1 缓存

  • L1：每个 SM 一个，和 shared memory 共用那块统一数据缓存。
  • L2：整块 GPU 共享，比 L1 大得多。
  • constant cache：每个 SM 一个，缓存 kernel 执行期间不变的值，kernel 参数也可能放这里（Module 4 的 02_constant_coeff.cu 会用到）。
离计算越近越快、越小、共享范围越窄。优化 GPU 程序，大半功夫是在“让数据少走远路”。

1.2.3.4Unified Memory：一个指针两边用

没有 unified memory 时，CPU 只能读 host memory，kernel 只能读 device memory，数据必须显式来回拷贝（图 5 的 ② 和 ⑤）。

Unified memory 让一次分配可以被 CPU 和 GPU 都访问，运行时或硬件会在需要时自动把数据迁移到正在用它的那一侧。代码写起来更省事，作业 02_vector_add_um.cu 就是这个版本。
