Session 1 · 配套读本的问答整理

GPU 问答复习本

这份复习本整理了阅读《GPU 从零读本 · 1.1–1.2》时提出的 8 个问题。每个问题先给结论，再给依据。

GPU 的数字以 A100 为例。CPU 的数字有两个来源：一部分是 AMD EPYC 7742 的公开规格，另一部分是在一台 Intel Xeon 2.30 GHz 云主机上的实测，这台机器没有 GPU。实测方法见文末。

线程与调度

Q1一个 SM 上同时有几个 warp？其中几个在运行，几个在等待？

A100 的一个 SM 最多驻留 64 个 warp。每个时钟周期最多有 4 个 warp 发出指令，其余的处于就绪或阻塞状态，比例由 kernel 决定。

驻留上限

每 SM 最多驻留的 warp 数 = 每 SM 最大驻留线程数 ÷ 32，具体数值取决于 compute capability（NVIDIA 给每代 GPU 架构编的版本号）。数据出自 Guide 附录 Compute Capabilities：

GPUcompute capability最大驻留线程 / SM最大驻留 warp / SM
A1008.0204864
RTX 30 / 40 系列8.6 / 8.9153648
H1009.0204864

你的卡：用作业 prob 0.2 测出的“最大常驻线程 / SM”除以 32。

每个周期的三种状态

A100 的每个 SM 分为 4 个分区，每个分区有 1 个 warp 调度器，最多驻留 16 个 warp。每个调度器每个周期最多为一个 warp 发出一条指令（出处：A100 架构白皮书）。在任一周期，驻留的 warp 处于以下三种状态之一：

状态含义A100 一个 SM 上的数量
issued（发出指令）本周期被调度器选中≤ 4
eligible（就绪）下一条指令可以执行，但本周期没被选中由程序决定
stalled（阻塞）在等 global memory 读取返回、前一条指令的结果、__syncthreads() 等条件由程序决定

“发出指令”和“正在执行”不是一回事。一个 warp 上个周期发出的访存指令还没返回时，这个周期另一个 warp 又可以发出指令，所以同时在流水线里执行的 warp 可以多于 4 个。

实测方法：运行 ncu --section SchedulerStats ./程序。这个命令会报告每个调度器平均的 Active Warps（驻留数）、Eligible Warps（就绪数）和 Issued Warp（每周期发出数）。如果 Eligible Warps 的平均值远低于 1，说明调度器经常在某些周期找不到可以发射的 warp，这些周期计算单元是空闲的。

实际驻留数受 block 资源用量限制

block 是整体分配到 SM 上的，所以实际驻留的 warp 数 = SM 能装下的 block 数 × 每个 block 的 warp 数。能装下几个 block，取决于以下三项中最紧的一项：

  • 寄存器：每线程寄存器数 × block 线程数，累加不能超过 SM 的 65,536 个。
  • shared memory：每个 block 的用量，累加不能超过 SM 可用的容量。
  • 每 SM 最多驻留的 block 数：A100 为 32。

下面是只受寄存器限制的 A100 例子，block 有 256 个线程（8 个 warp）：

每线程寄存器每 block 需要能装下的 block驻留 warp
32256 × 32 = 8,19265,536 ÷ 8,192 = 88 × 8 = 64（上限）
64256 × 64 = 16,384432（上限的一半）

实际驻留 warp 数与上限之比叫 occupancy。作业 prob 4.8 要求你用 shared memory 这一项限制在自己的卡上手算。

Q2warp 是 SM 的基本执行单位吗？它和 OS 线程像吗？

是的，warp 是 SM 调度和发射指令的单位。warp 和 OS 线程不像，它更接近 CPU 的 SMT 硬件线程（见 Q3）。

调度器每次选一个 warp，为它的 32 个线程发出同一条指令，被屏蔽的线程不执行这条指令。三个层级各有分工：

层级是什么的单位
thread编程：kernel 代码按单个线程编写
warp调度和发射指令
block分配资源：寄存器和 shared memory 按 block 分配，block 中所有线程结束后才释放

warp 与 OS 线程的区别：

对比项OS 线程在 CPU 上warp 在 SM 上
调度者操作系统内核（软件）warp 调度器（硬件）
切换粒度时间片，毫秒级每个时钟周期
切换开销本机实测约 0.75 μs零
何时离开处理器时间片用完、阻塞或被抢占一般驻留到所属 block 结束
一次调度执行几个线程132（同一条指令）

warp 切换开销为零，是因为每个驻留 warp 的程序计数器和寄存器在它的整个生命周期里都保存在片上：

“The execution context … for each warp processed by a multiprocessor is maintained on-chip during the entire lifetime of the warp. Therefore, switching from one execution context to another has no cost.”CUDA C++ Programming Guide（旧版），Hardware Multithreading 一节

代价是驻留数有硬上限：OS 可以把线程上下文换到内存里，从而支持远多于核数的线程，SM 不这样做，所以驻留的 warp 数受寄存器堆和 shared memory 的容量限制（Q1）。

Q3什么是硬件线程（SMT）？

硬件线程是 CPU 核里一份由硬件保存的线程状态，即一个 PC 和一套寄存器。一个核保存多份状态，就能在每个周期从不同的指令流中挑指令执行，切换开销为零。这种设计叫 SMT（Simultaneous Multithreading），Intel 的 SMT 实现商品名叫 Hyper-Threading。

1. 从 OS 线程说起

OS 线程是软件概念。操作系统内核为每个线程保存一份状态：程序计数器（PC）、各寄存器的值、栈指针。

没有 SMT 的 CPU 核，任一时刻只装着一份这样的状态。线程数多于核数时，内核用时间片轮流运行这些线程，换线程的步骤是：

  1. 把当前线程的寄存器存到内存；
  2. 从内存装入另一个线程的寄存器；
  3. 跳到新线程的 PC 继续执行。

这叫上下文切换。在本复习本的实验机上实测，一次切换约 0.75 μs，按 2.3 GHz 标称频率约合 1,700 个周期。

2. 问题：单个线程填不满核的执行单元

一个核只执行一个线程时，经常有很多周期没有指令可以发射。在同一台实验机上测得两个典型原因：

  • 依赖链：每条 double 加法都依赖上一条时，加法吞吐只有峰值的 25%（读本 §2，延迟 0.528 ns）。
  • DRAM 访问：一次随机读 DRAM 平均要 142 ns，后续依赖这个数据的指令在此期间都不能发射。

用 OS 上下文切换来填补这些空档不可行：一次切换 0.75 μs，是一次 DRAM 访问的 5.3 倍，是一次加法延迟的 1,400 倍。切换本身就比要填补的空档还长。

3. SMT：在硬件里同时保存多份线程状态

SMT 在一个核里放 2 份（或更多份）PC 和寄存器，执行单元、cache 等其余部分由这几份共用。每一份状态叫一个硬件线程，Intel 也称之为逻辑处理器（logical processor）。

核在每个周期可以从多个硬件线程中挑出可执行的指令来发射。一个线程在等 DRAM 时，另一个线程的指令可以使用空出来的执行单元。所有硬件线程的状态一直留在核里，切换不需要保存或恢复寄存器，开销为零。

4. 操作系统看到的是硬件线程

对操作系统来说，每个硬件线程都是一个独立的 CPU。Linux 的 lscpu 中：

  • Thread(s) per core：每核的硬件线程数。
  • CPU(s)：插槽数 × 每插槽核数 × 每核硬件线程数，即操作系统可以调度的 CPU 个数。

两个例子：

  • EPYC 7742：64 核，每核 2 个硬件线程，CPU(s) 为 128。
  • 本复习本的实验机：lscpu 显示 Thread(s) per core: 1，没有开启 SMT。

5. 两层调度

层把什么分配给什么调度者粒度
第 1 层软件线程（可有成千上万个）→ 硬件线程操作系统内核时间片，毫秒级

6. 与 warp 对照

GPU 的 SM 把第 2 层做得更宽：

Intel 核（开启 SMT）A100 的一个 SM 分区
硬件中保存的线程状态2 份最多 16 个 warp
每份状态的指令流宽度1 个线程32 个线程（SIMT）
每周期发射可同时发射两个硬件线程的指令选 1 个 warp 发射 1 条指令
切换开销零零

为什么 GPU 要保存更多份状态？CPU 主要靠乱序执行和大容量 cache 减少等待，GPU 没有乱序执行，每个线程分到的 cache 也小得多：

  • EPYC 7742：256 MB L3 ÷ 128 个硬件线程 = 每线程 2 MB。
  • A100：40 MB L2 ÷ 221,184 个驻留线程 = 每线程约 190 B。

所以 GPU 主要靠在 warp 之间切换来掩盖延迟，需要的线程状态份数也就多得多。

Q45 级流水线的 IF、ID、EX、MEM、WB 是什么意思？

这是计算机组成教材里经典的 5 级流水线：CPU 执行每条机器指令都依次经过这五个阶段。各阶段使用不同的硬件部件，所以多条指令可以错开一个阶段同时执行。

一条指令的五个阶段

以 RISC-V 指令 add x3, x1, x2（x3 = x1 + x2，x1、x2、x3 是寄存器）为例：

阶段全称做什么对 add x3, x1, x2
IFInstruction Fetch按 PC 地址从指令 cache 读出指令，PC 指向下一条读出这条指令的编码
IDInstruction Decode解析操作类型和寄存器编号，从寄存器堆读出操作数识别为加法，读出 x1、x2
EXExecuteALU 运算；load/store 在此计算地址计算 x1 + x2
MEMMemory Access只有 load/store 读写数据内存不做事
WBWrite Back把结果写回寄存器堆把和写入 x3

多条指令重叠执行

时钟周期 →   1    2    3    4    5    6    7    8    9
指令 1      IF   ID   EX   MEM  WB
指令 2           IF   ID   EX   MEM  WB
指令 3                IF   ID   EX   MEM  WB
指令 4                     IF   ID   EX   MEM  WB
指令 5                          IF   ID   EX   MEM  WB

每条指令仍需 5 个周期完成，这是延迟。从第 5 个周期起每个周期完成 1 条，这是吞吐。

数据冒险

后一条指令要用前一条的结果时，叫数据冒险（data hazard）。下面按无转发（forwarding）、寄存器堆在同一周期先写后读的经典模型分析：

指令 1：add x3, x1, x2     # 写 x3
指令 2：add x5, x3, x4     # 读 x3

时钟周期 →   1    2    3    4    5    6    7    8
指令 1      IF   ID   EX   MEM  WB
指令 2           IF   --   --   ID   EX   MEM  WB
                      ↑ 指令 2 的 ID 必须等到第 5 周期指令 1 写回 x3

空转的两个周期叫 stall 或 bubble。实际 CPU 用转发把 EX 的结果直接送给下一条指令，可以减少等待，但通常不能完全消除。读本 §2 的 K = 1 实验就是这种情况：每条 addsd 都要等上一条的结果，测得的是延迟（0.528 ns），不是吞吐（0.132 ns）。

用其他线程的指令填补空转

如果硬件保存着多个线程的 PC 和寄存器，IF 可以轮流从各线程取指。设同一线程相邻两条指令的 IF 相隔 T 个周期：

  • 生产者在第 c 周期 IF，第 c+4 周期 WB；
  • 消费者在第 c+T 周期 IF，第 c+T+1 周期 ID；
  • 不空转的条件是 c+T+1 ≥ c+4，即 T ≥ 3。

所以在这个模型下，3 个线程轮流取指就能完全消除空转：

时钟周期 →   1    2    3    4    5    6    7    8
A 的指令 1  IF   ID   EX   MEM  WB
B 的指令 1       IF   ID   EX   MEM  WB
C 的指令 1            IF   ID   EX   MEM  WB
A 的指令 2                 IF   ID   EX   MEM  WB
                                ↑ 第 5 周期 ID 读 x3，A1 同一周期先写入

只有 2 个线程时 T = 2，A 的指令 2 仍要空转 1 个周期。不同线程的指令访问的是不同的寄存器，彼此没有依赖，所以可以互相填补。所需线程数 3 和读本 §2 中“所需独立操作数 = 延迟 ÷ 发射间隔”是同一个规律。

真实的 CPU 和 GPU 流水线远多于 5 级，还有乱序执行、多发射等机制。5 级模型用来理解原理。

Q5OS 线程模型和 5 级流水线是什么关系？

两者是上下层的关系，不是同一层的子流程。上下文切换的每一步都由一串机器指令组成，而每一条指令都要走一遍 IF→ID→EX→MEM→WB。两个模型的交汇点是 PC 和寄存器堆。

第 1 层：操作系统（软件）
  上下文切换 = 3 步
    ① 保存当前线程的寄存器
    ② 装入另一个线程的寄存器
    ③ 跳到新线程的 PC
        │
        │ 每一步都是一串普通机器指令
        ▼
第 2 层：指令序列
  ① = sw x1, 0(sp)     把 x1 存到内存
      sw x2, 8(sp)     把 x2 存到内存
      ...（每个寄存器一条，几十条）
  ② = lw x1, 0(t0)     从内存读回 x1
      lw x2, 8(t0)
      ...（几十条）
  ③ = jr ra            跳转，改写 PC
        │
        │ 每一条指令都要依次走过 5 个阶段
        ▼
第 3 层：流水线（硬件）
  sw x1, 0(sp) → IF → ID → EX → MEM → WB
  sw x2, 8(sp) →      IF → ID → EX → MEM → WB
  ...

图中的 RISC-V 指令是示意。Linux 实际的切换路径还包括调度器选择下一个线程的代码，所以实测的 0.75 μs（约 1,700 个周期）远多于搬运寄存器本身所需的周期。

交汇点：PC 和寄存器堆

流水线阶段用到线程状态的哪部分
IF读 PC，决定取哪条指令
ID读寄存器堆
WB写寄存器堆

流水线本身没有“线程”这个概念。执行哪个线程，只取决于 IF 用哪个 PC、ID 和 WB 访问哪套寄存器。

统一起来看

概念在流水线模型中对应什么
一条指令依次流过 IF→ID→EX→MEM→WB 的一个工作项
一个线程一个 PC 加一套寄存器值，即一条指令流的来源
数据冒险同一条指令流中后一条等前一条的结果，流水线空转
OS 上下文切换用一串普通指令，把唯一的一份 PC 和寄存器换成另一个线程的

填补数据冒险的空转有三种办法：

  • 在同一条指令流里找独立指令：编译器改写代码，或者 CPU 乱序执行。
  • 在硬件里同时放多条指令流：SMT、warp 调度。

OS 切换线程不是为了填补这种空转，它太慢了（Q3）。它的作用是让更多软件线程轮流使用有限的硬件线程。

存储

Q6global memory 是离 SM 很近、由程序员手动管理的 cache 吗？

不是。global memory 是芯片外的显存，离 SM 最远、容量最大。离 SM 很近、由程序员显式管理的是 shared memory。

A100 40 GBglobal memoryshared memory
物理位置芯片外的 HBM每个 SM 内，与 L1 共用 192 KB SRAM
容量40 GB，整块 GPU每 SM 最多 164 KB
谁能访问所有线程；host 可用 cudaMemcpy 读写同一 block 内的线程
生命周期从 cudaMalloc 到 cudaFree，跨越多次 kernel launch所属 block 执行期间
是否经过缓存经过 L2，可能经过 L1，由硬件管理本身不是缓存，没有替换策略
管理方式程序员分配和释放，缓存行为由硬件决定程序员决定放什么、何时读写、何时同步

按离 SM 由近到远排列：寄存器（编译器分配）→ shared memory（程序员管理）与 L1（硬件管理）→ L2（硬件管理，全 GPU 共享）→ global memory → host memory（经 PCIe 或 NVLink 访问）。

Q7shared memory、L1、L2 的性能差不多吗？区别只在于是否由程序员管理吗？

在 A100 上，shared memory 和 L1 的延迟接近（23 和 33 个周期），L2 则慢得多（200 个周期，是 shared memory 的 8.7 倍）。shared memory 和 L1 的区别也不只是管理方式。

存储延迟（周期）约合（ns）与 shared load 之比
shared memory（load / store）23 / 1916 / 131×
L1 命中33231.4×
L2 命中2001428.7×
global memory（绕过缓存）29020612.6×

原因：shared memory 和 L1 是 SM 内同一块 SRAM；L2 在 SM 之外，由 108 个 SM 共享，访问要经过片上互连。

Q8程序员怎样管理 shared memory？

全部是显式管理：在 kernel 里声明数组，用普通赋值语句把数据从 global memory 搬进来，用 __syncthreads() 保证 block 内的写入完成后再读，最后把结果写回 global memory。block 结束时 shared memory 由硬件自动回收。

分配

// 静态分配：大小在编译时确定，每个 block 一份
__shared__ float buf[256];

// 动态分配：大小在 launch 时以字节数作为执行配置的第三个参数传入
extern __shared__ float buf[];

静态分配每个 block 最多 48 KB。要用到 48 KB 以上（A100 最多 164 KB），必须用动态分配，并且在 launch 前调用：

cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, 字节数);

最常见的四步写法

作业中 cuda/m3_simt/02_sync_matters.cu 给出的代码，把每个 block 负责的 256 个元素倒序：

__shared__ float buf[BLOCK];          // ① 声明
int base = blockIdx.x * BLOCK;
int t = threadIdx.x;
buf[t] = in[base + t];                // ② 装入：global → shared
__syncthreads();                      // ③ 同步：等 block 内所有线程写完
out[base + t] = buf[BLOCK - 1 - t];   // ④ 读另一个线程写入的元素，结果写回 global
  • 第 ② 步：硬件不会自动装入，必须由线程用赋值语句写入。
  • 第 ③ 步：__syncthreads() 让 block 内每个线程都停下，直到所有线程到达，保证第 ② 步的写入在第 ④ 步读取前完成。
  • 多轮复用同一块 shared memory 时，下一轮装入前还要再同步一次，否则有线程可能覆盖别的线程尚未读完的数据。

去掉第 ③ 步会出现什么现象、为什么，是 prob 3.3 的实验内容。

两种用途

  • 线程间交换数据：上例中线程 t 读的是线程 BLOCK−1−t 写入的值。若改用 global memory 交换，A100 上每次读取约 290 周期，shared memory 为 23 周期（Q7）。
  • 复用数据：同一个 global memory 元素被 block 内多个线程读取时，先读一次放进 shared memory，后续读取都按 23 周期计。作业 prob 4.2（stencil）和 Bonus（matmul）属于这一类。

异步复制

普通写法里，数据先从 global memory 读进寄存器，再写入 shared memory。较新的 GPU 提供了不经寄存器的异步复制，复制期间线程可以继续计算：

  • compute capability 8.0 及以上（含 A100）：cp.async 指令，C++ 中为 cuda::memcpy_async。
  • compute capability 9.0 及以上（如 H100）：TMA（Tensor Memory Accelerator），一次复制一整块多维数据。
